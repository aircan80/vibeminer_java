# Guided build browser and C build overview

**Implementation plan for the agreed two-screen workflow. Planning only; this document does not authorize source changes.** The dedicated milestone is “Guided discovery and build overview.” GitHub stories track delivery; no dates are implied.

The only implemented journey in this milestone is **guided Discover → Open Build → C Build overview**, with working per-build **On demand / Download all** behavior. The latest [discovery mockup](design/build-discovery/index.html?concept=guided) and [C overview](design/build-mining-home/index.html?concept=archive), together with their latest review amendments, define presentation. Earlier discovery layouts and home A/B concepts are superseded, not alternative implementations. Game Data, Files, Assets, Compare, Findings and research launchers are excluded. Existing research services can be reused internally without building their screens. Monitoring #95, GC/deletion and broader research features remain separate.

## Product behavior

Discover places the WoW-only Product dropdown immediately beneath “Which builds do you want to explore?” Each option shows exact product ID and a reviewed descriptive alias. Aliases are versioned presentation metadata, never identity or proof of compatibility. Unresolved WoW identities remain honestly labeled; supported decoder coverage does not determine whether an officially advertised product appears. Do not classify other games by a guessed name prefix.

Product selection automatically refreshes advertised metadata, with secondary manual Refresh for retry. It does not open a build or download game payloads. Show one list with All / Local / Currently advertised, combining durable local observations/retention with the latest successful check scope. A partial regional failure preserves the prior known region state and explicitly reports its incomplete check; it must not manufacture remote absence. Offline starts can show local builds without network. Refresh is an explicit product-selection action; restoring the screen does not perform an automatic network scan.

Persist first-seen dates, a first-successful-product-visit baseline and per-build Open acknowledgement. The first successful product visit establishes its baseline without marking every existing row New. Subsequent first observations of exact identities are “New to VibeMiner” until Open acknowledges that identity. Refresh, download and restart do not re-badge acknowledged builds or clear unacknowledged New markers. Failed, canceled or partial regional checks cannot establish an unseen region baseline. Repeated A→B→A preserves retrieval history and stable first-seen/acknowledgement; these local dates are not release age or publisher chronology.

Group region badges only when complete identity-bearing references agree: raw product/channel/version, BuildId, build/CDN configurations, ProductConfig and other declared identity-bearing references. Version text alone is insufficient. Grouping is a presentation key that omits region for equality comparison; original region-specific snapshots, receipts and routes are preserved. No region choice is required when those references agree. Select a deterministic supported preferred route within that group and disclose it in Source details; never substitute a different referenced build. Keep conflicting groups separate.

The inspector has one primary Open Build action. Opening minimum metadata is separate from completing the full payload inventory: authenticate/retain the exact configuration and supported ROOT/IN/catalog lookup prerequisites needed for this build overview, record their scope/proof, and open C while the wider inventory can still be Preparing with unknown totals. Catalog prerequisites that are missing or unsupported prevent opening as ready; a not-yet-sealed bulk manifest never masquerades as complete metadata for Download all. It reuses verified retained metadata, or acquires/verifies the missing required catalog inputs with visible progress, then automatically opens C. Failure remains on the exact selection with retry. Context changes/cancellation fence stale completions. There is no Prepare/Start/Save-workspace sequence and no separately managed duplicate workspace concept. Existing internal workspace storage may be adapted, but reopening the same build/scope reuses its state.

C preserves the approved simple logo and labeled Game/Edition, Product ID, Channel/Region, Exact Build and Locale header. Status is plain text; Retained is a separate column. Mode and activity are compact plain-text header summaries. Known scope-retention progress belongs in the separate Retained column, not the mode value; wire-transfer activity is a distinct operation observation. The On demand / Download all control lives in Build readiness, not the header. Keep one useful storage/content breakdown. Priority scheduling is behavior, not a permanent explanatory block, priority slogan or demo control. Unsupported future research destinations remain unavailable rather than fabricated functionality.

## Complete scope and honest readiness

Research locale and mining target platform are independent of the Java host OS. Do not silently equate a Linux host with a Linux game client. The Windows/enUS numbers in the browser mockups are authored examples, not proven selection semantics.

Download all must cover **all declared content variants in the admitted published-manifest closure**: ROOT memberships, IN entries, applicable DL/download-manifest content and the other dependencies required to establish and retain that exact content set. It must not download every EN record indiscriminately, use the small IN manifest as the game inventory, approximate all content with Item/ItemSparse, or redefine “everything” as a convenient supported subset while omitting an unparsed manifest. Configuration, catalog, locator and verification dependencies belong in the closure and its cost/storage accounting. Installation/patch-only machinery must be explicitly classified with protocol evidence rather than silently dropped.

First admit nonselective all-language/all-platform variants when platform/locale filtering is unproven. Preserve every variant reference and keep research Locale separate. A Windows/enUS-only scope can be introduced only with independently validated root flag/install/download tag semantics, including unknown-bit behavior. It is never inferred from a friendly edition name or the current host. The build overview must state the actual admitted scope simply; no speculative platform wizard is required. Unknown or unparsed manifest families, missing mappings, unsupported prerequisite grammar and unresolved scope closure prevent a complete claim. They may leave a useful retained partial state.

Three readiness states are independent of operation activity:

| Domain state / displayed status | Required evidence |
| --- | --- |
| NOT_READY / Not ready | Required Open Build metadata is missing, corrupt, incomplete or unsupported for this exact context. |
| PARTIAL / Partial | Required Open Build metadata is verified; wider inventory or selected content is not yet complete, including Preparing with unknown totals, zero payloads, unresolved candidates or incomplete bulk work. |
| FULL / Fully downloaded | Complete admitted inventory/dependency closure is sealed and every required canonical encoded object is currently verified retained. No unknown requirement remains. |

Downloading, paused/waiting, canceled and needs-attention are operation descriptions, not extra readiness states. On demand does not downgrade an already Full build. Encoded E/F/unknown payload modes can be fully retained through whole-encoded verification without being decrypted or decoded. Required ROOT/EN/IN/DL interpretation that cannot be authenticated/read blocks the inventory instead. Full is not an installable game, universally readable assets, verified decoded CKey for every payload or server-data completeness.

Retained percentage is verified encoded scope coverage, not wire-transfer progress or summed per-build disk usage. It is shown only for a complete known denominator; otherwise display Unknown, with measured bytes/objects where known. Do not turn unknown into zero or invent a percent while catalog resolution is still discovering requirements. Shared physical SHA-256 bytes are counted once in storage, separately from scope-attributed logical/encoded coverage. Recheck missing/corrupt physical evidence before trusting current readiness; a historical success or queued item is insufficient.

## Actual capability gaps

Existing code provides bounded selected-file lookup/acquisition, authenticated selected EN pages, full-root retention, shared CAS/canonical claims, source-worker permits/startup fencing, metadata repair, retention intents and narrow decoded research projections. These are valuable components, not a bulk downloader.

`SelectedRootLookup` streams selected caller IDs; it does not enumerate a whole inventory. `WowRootParser` materializes the supported TSFM v1/v2 subset and treats most flags as opaque. Existing full EN parsing materializes large maps; selected-page lookup is not a durable bulk index. IN entries/tags are not the full game catalog. DL and any other required current-content inventory interpretation must be implemented and reviewed where absent. Current compatibility is a pinned supported WoW format/build cohort, not every Retail/Classic/Forever build implied by the dropdown.

The milestone therefore includes real bounded full-inventory parsers, durable derived indexes and scope closure work. Add streaming/batched enumeration without holding millions of membership objects or creating one future per file. For the first durable catalog design, retain a complete required EN as **one encoded CAS object**, verify its admitted complete proof, and derive bounded indexes offline; do not persist session-only selected-page buffers beside a later duplicate full EN. New catalog kinds/proof capabilities must be explicit extensions to existing typed receipts, not relabeled ROOT/INSTALL proof. Decoder breadth progresses through an explicit format matrix and adversarial fixtures; unsupported inputs fail honestly rather than becoming empty successful catalogs.

## Layer and persistence contracts

A build-content application facade is the caller-facing access path: request content for an exact build/file identity without deciding whether bytes are local. Compose the existing resolution, verified shared-store reads, shared acquisition and priority scheduling behind narrow ports. Both interactive requests and bulk retention use this same path. The build repository stores records and references; the object store owns bytes; parsers and transports remain separate adapters. This is a coordinating responsibility, not a new monolithic repository or permission to create a parallel download/cache implementation.

Domain/application own immutable grouped build references, exact opening context, a versioned scope definition, metadata readiness, sealed inventory requirements, policy intent and typed operation outcomes. Infrastructure owns official transport, pure format adapters, SQLite and CAS; JavaFX owns presentation and request epochs. No HTTP, parser, SQL or filesystem work in controls. New boundaries should compose existing services through narrow ports rather than expand a generic job/proof framework.

A durable manifest is keyed by exact metadata proof and scope/interpretation revision; changing scope creates a different immutable manifest. Preserve ROOT/IN/DL variant references separately, deduplicate desired game content by verified namespace+CKey, choose one allowed actual EKey and preserve its real source receipt. Do not silently retain a second encoding for the same canonical content. Reuse of existing A under another build requires the current association proof, not a fabricated B receipt; incompatibility is a replan/conflict, not permission to duplicate. Keep the existing shared actual-worker nonce and one opaque store-session startup fence across every producer.

Persist compact paged work records, not a list of live futures for every manifest entry. Bound in-memory pages, subscriber counts, transfers, verification workers, retries and locator sessions. Record verified prospective identity before promotion; complete canonical publication separately from each surviving consumer's association/pin. Queue/manifest publication and consumer updates are transactional, with corruption and crash tests. No new partial-file cache or per-build payload folders. Resume initially means object-boundary work recovery: partial whole-object staging is discarded/retried under existing policy; do not promise byte-range resume. Preserve completed CAS objects across retries and mode changes.

Foreground admission must bypass the remaining bulk queue; reserve bounded capacity and yield bulk between already bounded requests/ranges. Joining foreground demand promotes the same flight instead of a second transfer. Bound fairness/starvation and backpressure without promising zero latency or unsafe interruption. Turning bulk off cancels queued bulk intent and withdraws its in-flight consumer only; actual shared I/O retires under the existing owner rules. Mode, activity and readiness are separate persisted/read models.

Preflight declared additional payload, metadata/index and temporary storage against quotas and observable free space with safety headroom. Recheck before allocating/publishing bounded objects; disk-full remains typed and preserves old objects/references. Unknown sizes prevent a total promise and may stop admission under policy rather than allocate unbounded storage. Accounting must distinguish known additional bytes, unresolved requirements and global unique bytes. No GC/reclaimable-space claims or deleting reader-leased content are part of this work.

Persist Download all mode only after explicit authorization for that exact scope. Startup may resume this prior intent under the stored limits and mode; it must not discover new builds, expand scope, follow latest pointers or scan upstream automatically. Restoring an On demand build/home causes no network work. An interrupted owner becomes recovery work through the existing exclusive store/session fence; never clear another active producer's nonce or infer verified content from queue state.

## TDD and acceptance

Each story starts with a meaningful behavior/format fixture failure, then the smallest implementation, independent review and clean integration checks. Core tests are deterministic/offline; network mechanics use controlled local transports, not live CDN assumptions. Test complete inventory proof and scope exclusions with independent parser fixtures; streaming memory/page bounds; millions-of-entry queue admission without millions of futures; opaque payload retention versus unreadable required metadata; unknown size/404/corruption/disk-full/quota refusal; canonical alternate-encoding exclusion and cross-build physical sharing; prospective/promotion/association crash boundaries; and cold restart with mode On demand versus explicitly authorized Download all.

Discovery/Open tests cover full reference equality/group split, regional receipts, zero-network local fast path, first-seen/New baselines, partial regional failure, offline with/without local observations, metadata acquisition/verification retry and canceled/stale completion. Scheduler tests saturate bulk, admit foreground independently, promote same-object work, cancel each consumer separately, turn bulk off/on and verify no duplicated bytes or early owner release.

Native JavaFX acceptance uses the two actual screens at 1280×800 and 1440×1100, 100% and 200% text, with keyboard/focus and offline/restart fixtures. Product precedes results; Open is reachable; full exact identity/status/retained/mode remain readable; readiness control is in the body; no A/B cards, hidden research implementation or priority explanatory UI appears. Prototype quantities never become production evidence. Follow the [build-browser acceptance matrix](BUILD-BROWSER-ACCEPTANCE.md) for detailed fixture gates and the [reviewed story breakdown](BUILD-BROWSER-STORIES.md) for issue allocation. The outcome steps above may split into multiple small parser/persistence/application stories; they do not replace those acceptance gates.


## Decisions to close before each production admission

The default inventory is all declared language/platform variants until proven selectors exist; research Locale remains a view preference. An edition label never bypasses format admission. Open can show C after its precise minimum catalog contract is satisfied, while complete inventory preparation remains visible and the denominator unknown. Download all intent may include preparing the rest of the catalog under the same stored limits; On demand does not secretly finish that bulk work in the background.

Use the existing foreground capacity shape as the initial scheduler envelope: at most four active transfer jobs globally, at most two bulk transfers, at least one slot reserved for interactive admission; bounded verification work uses its own existing bounded pool. Start with at most128 durable work rows per in-memory page, two prefetched pages, and32 consumers per shared flight. These are implementation policy limits, not guarantees about the upstream inventory; require threshold/backpressure/fairness tests and revise through reviewed policy versions rather than unbounded queues.

Before enabling real bulk retention, freeze tested per-object, metadata-wire, decoded-work, manifest-row, retry, additional-storage and temporary-space limits in a persisted policy. Derive defaults from admitted full-scope fixtures and actual supported manifests, not mockup size figures or selected-file defaults. Missing free-space information, unbounded declarations or a plan exceeding that policy must pause/refuse admission explicitly; they never authorize unlimited storage or a Full claim. This is a required acceptance gate in inventory/execution stories, not a reason to ship a toggle without its downloader. There is no user question blocking this plan: unsupported source shapes stay visible with precise rationale while their grammar/limits receive the needed backlog story.
