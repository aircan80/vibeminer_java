# One selected Item evidence export

**Status: approved design proposal tracked in [#91](https://github.com/aircan80/vibeminer/issues/91), child of #25/#9. No implementation until #83/#89 qualification and the next alpha checkpoint.** This does not close broader export, relation or historical-build stories. The existing [physical Item](ITEM-PROJECTION.md), [paired-name](ITEM-NAMES.md) and [search](ITEM-NAME-SEARCH.md) contracts remain the capability boundaries.

Export exactly one inspected physical Item record, with optional explicitly selected already prepared name context. The user receives a portable, self-describing finding without hidden acquisition or expanded coverage. This is JSON reproducibility metadata and commitments; it cannot authenticate itself as Blizzard evidence without the underlying source/proof context.

## Acceptance

- Explicit export from one supported inspected physical Item row; preview Item record ID, exact source context, Item-only versus explicitly included prepared-name context, partial coverage, JSON format and destination. No automatic preparation, acquisition, repair, latest substitution, external publication or store membership/pin mutation.
- Use one narrow backend snapshot operation that holds both applicable current source leases through the same final SQL context/row read; return the immutable selected row and a separately measured verification window. Do not concatenate independent lookups or treat historical prepared handles as fresh observation. An outdated pair/artifact, missing/corrupt/unready source or incompatible interpretation returns a typed failure with no successful output. Item-only can be chosen explicitly; never silently downgrade promised paired evidence.
- Versioned strict UTF-8 JSON distinguishes itemRecordId, itemTableFileDataId and optional sparseTableFileDataId, with physical/section ordinals. Each integer retains width-tagged raw bit-pattern hex and physical interpretation separately from attributed candidate value/sign/width/DBD binding. Preserve lossless wide values; Java signed storage does not determine raw-bit signedness.
- Name state is explicit: NOT_INCLUDED for Item-only; PHYSICAL_NAME with exact Unicode and valid empty string; COPY_UNINDEXED with known copySourceId but no inherited name; NO_PHYSICAL_MATCH limited to admitted coverage. No copied names or other-build/locale fallback.
- Include exact build/product/region/locale/configs, actual encoded representations/physical identities, both applicable source scopes, decoder/artifact/schema provider/revision/digest/license/attribution, section/copy/excluded coverage, complete encoded proof and admitted decoded windows/chunks/revisions. Full decoded attestation is optional and absent/null means unverified. Never infer full-table CKey from selected windows.
- Historical source receipts and decoded-window proof timestamps remain distinct from current physical verification observations and export time. Replay does not refresh historical proof; preserve historical localVerification/chunk/source timestamps unchanged and record the new measured verification interval separately. JSON is reproducibility metadata/commitments, not an independently self-authenticating Blizzard proof package.
- Fixed version-1 envelope ceiling is 2 MiB of encoded UTF-8, enforced during bounded encoding. Valid supported source proofs may exceed this ceiling: a source permits up to 2 MiB binary proof, a pair has two, and JSON encoding expands them. Disclose this export restriction; oversize metadata/receipts fail LIMIT_EXCEEDED with no output rather than truncate or silently substitute proof hashes. Measure an authored 3,780-chunk receipt before promising the current cohort fits; no source bytes/raw DBD/full-table payloads or unselected rows. Scope is one record only.
- Write through a temporary sibling with a tested explicit destination-race policy. Java ATOMIC_MOVE does not portably guarantee no-clobber when a target races into existence; a preflight exists check is insufficient. Qualify strict no-clobber or separately consented replacement against the actual adapter/filesystem, and refuse unsupported atomic policy rather than silently copying/truncating; cancellation, disk/permission/invalid-destination failure and oversize output leave no falsely completed file or damaged existing target. No app-private logs, credentials or unrelated machine paths enter JSON.
- Deterministic unit/real temporary-file/SQLite/CAS tests plus native authored-data export preview/save/cancel/failure/keyboard/scaling journey pass offline. Inspect resulting JSON using an independent parser and public schema. No actual game row/name contents copied into fixtures/docs.

## TDD gates

Exact identity/proof/attribution envelope; width/hex/wide integer boundaries; strict Unicode including supplementary and composed/decomposed strings; all four name states; source/pair/generation replacement; old-proof versus fresh-physical timestamps; current source corruption; byte-ceiling refusal; cancellation/atomic destination/overwrite preservation; no network/pin/membership effects; no private or unrelated fields.

Excluded: CSV, bulk/pages/query exports, notes/notebook, relation discovery, asset conversion, new source acquisition, older-build availability, new locale/build/schema, whole decoded-CKey upgrades, comparisons, GC and external publishing. #18 historical evidence remains a separate priority. No implementation or release is authorized by creation of this planning story.

## Minimal layered boundary

Application owns one explicit export use case and pinned selection descriptor: exact Item artifact/context and positive record ID, plus optional exact prepared pair. The selection is input identity, not authority to trust a previously displayed row. A narrow read-only snapshot backend holds both applicable current source leases through the same final SQL context/row read and returns bounded immutable evidence with a measured verification interval. Existing lookup results alone are insufficient: their prepared evidence is historical. Preserve historical proof timestamps unchanged; the export interval is a separate observation. No export path invokes preparation, transport or repair. Use the existing bounded worker/cancellation conventions; this is not a generic query or exporter framework.

The application snapshot is plain domain/application data with no JDBC, JavaFX, parser object, open response or machine path. Schema version and fixed limits are explicit. A narrow infrastructure writer receives that snapshot and the explicitly chosen destination, enforces byte limits while encoding strict UTF-8 JSON, writes a bounded sibling temporary file and finalizes only after complete successful output. Destination/overwrite selection remains a desktop input; policy and real I/O belong to use cases/adapters. Do not expose a writable stream to UI controls or parse live table bytes in the encoder.

Retain both applicable source leases through the single snapshot transaction and final context/row check; define the immutable snapshot commit point before asynchronous encoding. A completed snapshot reports verification at its actual observation time, not a guarantee that source files remain unchanged forever after export. Cancellation after atomic completion may lose to committed success; record the actual terminal outcome rather than falsely relabeling a completed file as partial. Inject time and destination failures for deterministic tests.

Use a fixed JSON version with an independently consumed schema. Version 1 permits at most 2 MiB UTF-8, one physical Item record, four admitted integer candidates and at most one optional name result. Existing source/receipt/list bounds remain active before encoding; the output ceiling is additional, not permission to materialize unbounded input. Reject invalid Unicode or oversize output rather than replacing/truncating values. No persisted query ledger, alternate shared-content copy or schema migration is required for an explicit user export.

An exported file is intentional user output; it is not an archive/cache copy silently retained per build. A repeated explicit export can create another user file without changing internal deduplication or retention policy. Do not claim reclaimed store bytes or a retained full build from this operation.

## Destination and size feasibility gates

Before implementation promises strict no-clobber, demonstrate the actual filesystem adapter’s behavior when a target appears between selection and finalization, when an existing target was explicitly approved for replacement, and when atomic publication is unsupported. Java `Files.move` with `ATOMIC_MOVE` ignores other move options and leaves existing-target behavior implementation-specific; therefore an exists check plus atomic rename does not by itself prove no-clobber. Refuse policies the platform cannot uphold and preserve existing targets on failure. No silent non-atomic copy or truncating fallback. See the [JDK 25 move contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...)).

The 2 MiB output ceiling is an explicit version-1 restriction, not proof that every otherwise supported source can be exported. Paired valid binary receipts can already exceed it before JSON expansion. Add real-shaped authored 3,780-chunk proof measurement and over-limit tests; fail with no completed target and no truncated/hash-substituted evidence if it cannot fit. A later ceiling or envelope redesign requires a separately reviewed scope decision.
