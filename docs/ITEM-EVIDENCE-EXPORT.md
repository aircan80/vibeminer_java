# One selected Item evidence export

**Status: approved contract tracked in [#91](https://github.com/aircan80/vibeminer/issues/91), child of #25/#9. Application-contract TDD has started after #83/#89 qualification and independently verified alpha.6 assets; export is not yet delivered.** This does not close broader export, relation or historical-build stories. The existing [physical Item](ITEM-PROJECTION.md), [paired-name](ITEM-NAMES.md) and [search](ITEM-NAME-SEARCH.md) contracts remain the capability boundaries.

Export exactly one inspected physical Item record, with optional explicitly selected already prepared name context. The user receives a portable, self-describing finding without hidden acquisition or expanded coverage. This is JSON reproducibility metadata and commitments; it cannot authenticate itself as Blizzard evidence without the underlying source/proof context.

## Acceptance

- Explicit export from one supported inspected physical Item row through one progressive dialog: Scope → Verify immutable local snapshot → Destination and final path-bound authorization. Item-only is the default; including an already prepared exact name pair requires explicit selection. Preview Item record ID, exact source context, partial coverage, JSON format and destination. Enter is never a default Save action. No automatic preparation, acquisition, repair, latest substitution, external publication or store membership/pin mutation.
- Use one narrow backend snapshot operation that holds both applicable current source leases through the same final SQL context/row read; return the immutable selected row and a separately measured verification window. Do not concatenate independent lookups or treat historical prepared handles as fresh observation. An outdated pair/artifact, missing/corrupt/unready source or incompatible interpretation returns a typed failure with no successful output. Item-only can be chosen explicitly; never silently downgrade promised paired evidence.
- Versioned strict UTF-8 JSON distinguishes itemRecordId, itemTableFileDataId and optional sparseTableFileDataId, with physical/section ordinals. Each integer retains width-tagged raw bit-pattern hex and physical interpretation separately from attributed candidate value/sign/width/DBD binding. Preserve lossless wide values; Java signed storage does not determine raw-bit signedness.
- Name state is explicit: NOT_INCLUDED for Item-only; PHYSICAL_NAME with exact Unicode and valid empty string; COPY_UNINDEXED with known copySourceId but no inherited name; NO_PHYSICAL_MATCH limited to admitted coverage. No copied names or other-build/locale fallback.
- Include exact build/product/region/locale/configs, actual encoded representations/physical identities, both applicable source scopes, decoder/artifact/schema provider/revision/digest/license/attribution, section/copy/excluded coverage, complete encoded proof and admitted decoded windows/chunks/revisions. Full decoded attestation is optional and absent/null means unverified. Never infer full-table CKey from selected windows.
- Historical source receipts and decoded-window proof timestamps remain distinct from current physical verification observations and export time. Replay does not refresh historical proof; preserve historical localVerification/chunk/source timestamps unchanged and record the new measured verification interval separately. JSON is reproducibility metadata/commitments, not an independently self-authenticating Blizzard proof package.
- Fixed version-1 envelope ceiling is 2 MiB of encoded UTF-8, enforced during bounded encoding. Valid supported source proofs may exceed this ceiling: a source permits up to 2 MiB binary proof, a pair has two, and JSON encoding expands them. Disclose this export restriction; oversize metadata/receipts fail LIMIT_EXCEEDED with no output rather than truncate or silently substitute proof hashes. Measure an authored 3,780-chunk receipt before promising the current cohort fits; no source bytes/raw DBD/full-table payloads or unselected rows. Scope is one record only.
- Write through a temporary sibling with explicit authorization to replace the exact chosen pathname at commit, even if it was absent during preview. Qualify atomic replacement/refusal against the actual adapter/filesystem; strict no-clobber is outside this initial policy. Oversize output, pre-commit cancellation and failures known to precede publication leave the destination unchanged. A confirmed publication refusal preserves the existing target; an indeterminate provider outcome is reported as uncertain, without a universal preservation claim or fabricated success. Never silently copy, truncate the target or attempt destructive rollback. No app-private logs, credentials or unrelated machine paths enter JSON.
- Deterministic unit/real temporary-file/SQLite/CAS tests plus native authored-data export preview/save/cancel/failure/keyboard/scaling journey pass offline. Inspect resulting JSON using an independent parser and public schema. No actual game row/name contents copied into fixtures/docs.

## Minimal layered boundary

Application owns one explicit export use case and pinned selection descriptor: exact Item artifact/context and positive record ID, plus optional exact prepared pair. The selection is input identity, not authority to trust a previously displayed row. A narrow read-only snapshot backend holds both applicable current source leases through the same final SQL context/row read and returns bounded immutable evidence with a measured verification interval. Existing lookup results alone are insufficient: their prepared evidence is historical. Preserve historical proof timestamps unchanged; the export interval is a separate observation. No export path invokes preparation, transport or repair. Use the existing bounded worker/cancellation conventions; this is not a generic query or exporter framework.

The application snapshot is plain domain/application data with no JDBC, JavaFX, parser object, open response or machine path. Schema version and fixed limits are explicit. A narrow infrastructure writer receives that snapshot and the explicitly chosen destination, enforces byte limits while encoding strict UTF-8 JSON, writes a bounded sibling temporary file and finalizes only after complete successful output. Destination/overwrite selection remains a desktop input; policy and real I/O belong to use cases/adapters. Do not expose a writable stream to UI controls or parse live table bytes in the encoder.

Retain both applicable source leases through the single snapshot transaction and final context/row check; define the immutable snapshot commit point before asynchronous encoding. A completed snapshot reports verification at its actual observation time, not a guarantee that source files remain unchanged forever after export. Cancellation after atomic completion may lose to committed success; record the actual terminal outcome rather than falsely relabeling a completed file as partial. Inject time and destination failures for deterministic tests.

Use a fixed JSON version with an independently consumed schema. Version 1 permits at most 2 MiB UTF-8, one physical Item record, four admitted integer candidates and at most one optional name result. Existing source/receipt/list bounds remain active before encoding; the output ceiling is additional, not permission to materialize unbounded input. Reject invalid Unicode or oversize output rather than replacing/truncating values. No persisted query ledger, alternate shared-content copy or schema migration is required for an explicit user export.

An exported file is intentional user output; it is not an archive/cache copy silently retained per build. A repeated explicit export can create another user file without changing internal deduplication or retention policy. Do not claim reclaimed store bytes or a retained full build from this operation.

## Destination and size feasibility gates

Before implementation promises strict no-clobber, demonstrate the actual filesystem adapter’s behavior when a target appears between selection and finalization, when an existing target was explicitly approved for replacement, and when atomic publication is unsupported. Java `Files.move` with `ATOMIC_MOVE` ignores other move options and leaves existing-target behavior implementation-specific; therefore an exists check plus atomic rename does not by itself prove no-clobber. The initial policy instead requires explicit replacement-at-commit authorization for the chosen pathname, regardless of its preview-time existence; it does not promise strict no-clobber. Refuse policies the platform cannot uphold. Preserve the target on failures known to precede publication or confirmed publication refusal. If a provider failure leaves commit uncertain, report that outcome and leave the destination for inspection rather than asserting the old target survived or attempting rollback. No silent non-atomic copy or truncating fallback. See the [JDK 25 move contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...)).

The 2 MiB output ceiling is an explicit version-1 restriction, not proof that every otherwise supported source can be exported. Paired valid binary receipts can already exceed it before JSON expansion. Add real-shaped authored 3,780-chunk proof measurement and over-limit tests; fail with no completed target and no truncated/hash-substituted evidence if it cannot fit. A later ceiling or envelope redesign requires a separately reviewed scope decision.


## Destination qualification and bounded-size evidence

The progressive dialog first selects scope without I/O, then explicitly verifies one immutable retained-only snapshot. Destination selection and final path-specific authorization follow verification; choosing or changing a destination does not rerun source preparation or refresh historical proof. The final action must explicitly authorize replacement at commit for that exact pathname, including a file created there after preview. A different path requires new authorization. Show the 2 MiB ceiling rather than an unsupported promise that a prepared pair fits. An exact byte preview, if provided, must use the same bounded encoder and immutable snapshot as output.

The initial adapter should create a sibling temporary file with CREATE_NEW, finish bounded strict UTF-8 encoding, close the file, check cancellation, then request ATOMIC_MOVE. Provider-specific replacement/refusal behavior must be qualified on Windows, macOS and Linux. JDK ATOMIC_MOVE ignores other move options and does not guarantee create-only behavior when the target already exists; a prior existence check does not repair that race. Strict no-clobber would require a separately qualified primitive and is outside this initial policy. Unsupported atomic moves or replacement refusal must not trigger delete-target, truncation or copy fallback. Atomic visibility is not a claim of power-loss durability. [JDK 25 Files documentation](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/Files.html).

A successful atomic publication is the output commit point. Cancellation after that point may lose to committed success, which must retain its actual terminal receipt. For a provider failure whose commit outcome cannot be determined, report that uncertainty and preserve the destination for inspection; do not invent success, assert universal preservation of the previous target, or attempt destructive rollback. Cleanup removes only the writer-owned temporary entry when safe. Tests must cover a target created after preview, existing-target refusal, unsupported atomic publication, cancellation on both sides of commit and injected indeterminate outcomes.

A provisional authored full-shape sizing probe used current Java DTO record shapes with one Item definition/evidence/coverage/four-value row, a Sparse definition/evidence/coverage with 3,780 chunk attestations, nested source associations and receipts, a maximum-length Display made of 65,530 backslashes, and a separate verification observation interval. Compact reflection-based JSON measured:

| Per-chunk revision text | Authored envelope UTF-8 bytes |
| --- | ---: |
| 12 ASCII characters | 829,557 |
| 400 ASCII characters | 2,296,197 |
| 400 backslashes | 3,808,197 |

These figures were independently rerun, but are feasibility observations only: the private reflection probe is not the frozen public encoder, and its independently authored Item and Sparse fixtures are not an authenticated production pair. The short-revision result does not promise that the supported cohort or every valid source fits. The selected name also is not a universal worst-case JSON escape expansion. A future public encoder must measure its complete schema, raw-bit/unsigned formatting, identifiers, proof lists, attribution and exact Unicode escaping with authored inputs. Valid inputs exceeding the ceiling remain explicit LIMIT_EXCEEDED outcomes with no reduced evidence file. These measurements do not establish implementation acceptance.

## Approved cross-layer contract

New values and ports belong in `application.itemexport` and compose existing domain records; no new domain module or generic export framework is required.

- `ItemEvidenceSelection(PreparedItemProjection item, long recordId, Optional<PreparedItemNames> names)` pins a positive unsigned Item record ID. An included pair must contain exactly the selected Item handle. Displayed rows, search cursors and inferred name companions are not authority.
- `ItemEvidenceSnapshot(selection, ItemPhysicalRow row, Optional<ItemNameMatch> name, Instant verificationStartedAt, Instant verificationCompletedAt, String generationFingerprint)` contains the re-read physical Item and optional exact name result. The name is present exactly when paired evidence was selected. An empty optional means NOT_INCLUDED; the existing name result distinguishes physical empty strings, COPY_UNINDEXED and scoped NO_PHYSICAL_MATCH. The snapshot retains original definitions, coverage and historical evidence through its selection. Its generation fingerprint is sampled in the final SQL transaction and is an observation, not a replacement source identity or restart authority.
- `ItemEvidenceSnapshotBackend.capture(selection, CancellationToken)` is a blocking retained-only operation. It authenticates stored manifests before source verification and holds both applicable source leases through one final SQL context/row read. Item-only never touches Sparse. A missing or copy-only Item cannot become a successful physical-record export. No source lease survives the immutable snapshot return.
- `ItemEvidenceService.capture(selection)` returns an asynchronous snapshot. `save(snapshot, String authorizedReplacementPath)` returns a small `SaveOperation` with `completion()` and `requestCancellation()`. Its completion is a read-only stage representing the actual terminal outcome; canceling a derived observation future does not cancel the authoritative save. A confirmed save returns `ItemEvidenceReceipt(encodedUtf8Bytes, sha256, committedAt)`. An uncertain provider commit is a typed COMMIT_UNCERTAIN failure, never a fabricated receipt.
- `ItemEvidenceWriter.publish(snapshot, String authorizedReplacementPath, CancellationToken)` is the blocking bounded encoder/publication port. It receives no open source stream or database lease. The destination must be the exact displayed and authorized absolute lexically normalized pathname; reject a path requiring silent normalization. Do not resolve it into an inode identity or claim no-clobber. Paths are writer inputs only and are excluded from JSON.

The service permits one actual capture or save job at a time and retains at most one issued immutable snapshot. It validates the backend result's complete selection, physical row/coverage, name context and verification interval before issuance; a caller-supplied or altered snapshot cannot be saved. Accepted new capture admission immediately revokes the prior snapshot. Invalid, BUSY, CLOSED or executor-rejected requests do not revoke it. Once a new capture is accepted, failure or cancellation does not restore the previous authorization. Only validated success issues the new snapshot. Executor rejection is treated as no actual admission; direct executors that finish synchronously must not have their freshly issued snapshot cleared afterward. No I/O or future completion occurs while holding the service monitor.

Actual capacity remains occupied until the Runnable retires, including queued cancellation or I/O that ignores cancellation. Executors and shared resources remain caller-owned. Closing the service closes admission and requests cancellation without releasing source leases or the owner prematurely. Save cancellation is a request checked before publication, not immediate loss of the terminal result. There must be no post-writer cancellation check that turns confirmed publication into failure. Saving an issued historical snapshot does not reverify sources, refresh its observation interval or claim those sources are still current at save time.

A backward wall-clock interval during capture fails before issuing a snapshot; do not clamp or invent verification times. JSON uses `documentCreatedAt`, sampled before encoding, as its document creation observation. It does not contain the later actual commit timestamp. Receipt `committedAt` is sampled after confirmed publication and remains separate from the document. If the wall clock rolls backward after publication, preserve that actual receipt observation and the known successful outcome; do not fabricate causal ordering, rewrite the committed JSON, or relabel success as cancellation/failure. Historical proof timestamps remain unchanged throughout.

JSON must explicitly project the approved public fields rather than recursively serialize Java records. In particular, nested `BuildSnapshot` evidence can contain `SourceDocument.bytes`; those raw documents, source payloads, raw DBD text, private diagnostics and machine paths must never enter the export. Include the promised identities, config commitments, receipt facts, complete chunk/window lists, interpretation, schema attribution and coverage without payload bytes. The public schema must reject undeclared fields recursively. Encode each raw integer as zero-padded hexadecimal of `ceil(width / 4)` digits with explicit width and zero unused leading bits. Encode attributed candidate values as signed or unsigned decimal strings according to their declared sign, including unsigned 64-bit bit patterns; Java's signed `long` representation does not change that interpretation.

## Contract-first implementation gates

Release qualification is complete. First test the application values and service admission, issued-snapshot validation and terminal-outcome contract. Once those ports freeze, the retained snapshot adapter and explicit bounded JSON/writer can be implemented independently. Runtime composition and the single progressive desktop dialog follow accepted backend, service and writer checks; no new database schema, acquisition path or retained-content copy is needed.

Required tests include exact selection/row/proof substitution; both leases and the single SQL snapshot boundary; unchanged historical evidence versus measured verification time; Item-only and all paired-name states; current source corruption; raw-width/signed/unsigned-64 independent integer oracles; strict Unicode and exact JSON escaping; independent parsing against a closed public schema; canary source bytes/private paths excluded; full 3,780-chunk authored envelope and valid oversize refusal; and exact UTF-8 ceiling enforcement. Service tests must cover accepted versus rejected capture revocation, executor rejection, synchronous execution, admitted cancellation/failure without old-snapshot restoration, one-job retirement, and cancellation of observation futures without hiding confirmed save results. Writer/native tests must separately cover pre-commit cancellation, commit winning cancellation, target races, confirmed refusal, unsupported atomic publication, indeterminate outcomes and post-commit clock rollback.
