# Research areas: from build evidence to game questions

Status: research proposal for [#116](https://github.com/aircan80/vibeminer/issues/116), researched 2026-10-18. This does not expand the current build-workflow milestone or the next Tables milestone. The selected direction remains top navigation for areas, with an area's own navigation inside it; the table catalogue stays on the left.

VibeMiner should offer two ways to explore the same evidence. Tables, Files and Assets expose the underlying build. Later game-oriented views should answer useful questions by joining that evidence into readable context. An Items screen that merely renames a table adds little value; showing a named item with its classification, appearance references, requirements and the evidence behind each field does.

## Boundaries and navigation proposal

Use understandable area names rather than putting “low level” and “high level” in the main navigation. Home and Tables are the agreed near-term destinations. Files and Assets remain technical research candidates. Future game areas should earn a destination through a coherent workflow, not through the existence of a similarly named DB2. A World area could eventually contain maps, routes and encounters; that grouping is a proposal requiring user review, not a new approved menu.

Each semantic result must offer **Inspect source**: jump to the exact source table row, field or asset without losing the build/locale context. Preserve navigation back to the readable view. A relationship graph is useful only where its edge meanings are known and it answers a question; it must not substitute an unlabelled web of IDs for an explanation.

| Foundation | What it enables | Honest boundary |
| --- | --- | --- |
| Tables | Browse records, types, fields, validated references and optional labels; inspect unknown fields. | A schema description is not the build's actual data or proof of gameplay semantics. |
| Files | Find identities, sizes, representations and availability; inspect provenance and manifest membership. | A filename supplied by a community list is an annotation, not a Blizzard-authored filename fact. |
| Assets | Preview supported images, sounds and eventually models/maps, with dependencies. | A model or sound in a build does not establish its use, release date or obtainability. |
| Game-oriented views | Answer a question with related, named records and optional contextual evidence. | Client records do not establish complete live server behavior. |

## Evidence researched

The following examples were checked against WoWDBDefs revision **b9a63096cdd99b26967f17f9515377ae62cadfd7**. Its COLUMNS sections describe the union of fields across versions: a listed field does **not** prove that field exists in a selected build. An implementation must admit an exact BUILD/LAYOUT, validate the decoded file and inspect that layout's fields. The [format specification](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/README.md) defines explicit foreign targets, unverified names, localized strings and layout selection. Names, guessed comments and matching integer values alone are insufficient join evidence.

| Candidate and useful question | Evidence and minimum starting dependencies | Missing context and important limits |
| --- | --- | --- |
| **Items:** “What is this item, how is it classified, and which supported attributes changed?” | [Item](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/Item.dbd), [ItemSparse](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/ItemSparse.dbd), [ItemClass](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/ItemClass.dbd), supported icon decoding. Item.ClassID explicitly targets ItemClass.ClassID, **not ItemClass.ID**. Names and descriptive fields exist in ItemSparse layouts. | Prove the exact Item/ItemSparse cohort join and admitted row kinds rather than assuming every record is present. Item level and flags do not by themselves establish final scaled character stats, drop sources or obtainability. Comparison is a separate future capability, not an implicit dependency of the first readable item view. |
| **Maps and flight routes:** “Where does this route go, and how do these nodes connect?” | [Map](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/Map.dbd), [UiMap](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/UiMap.dbd), [TaxiNodes](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/TaxiNodes.dbd), [TaxiPath](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/TaxiPath.dbd), [TaxiPathNode](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/TaxiPathNode.dbd). Coordinate conversion, floor/instance, direction, node ordering and conditions need separately validated rules. A path existing in client data does not prove it is accessible to a particular faction/character or currently enabled. Terrain rendering is a larger asset dependency and is not required for a first textual route explorer. |
| **Creatures/NPCs:** “What named creature/display is referenced here?” | [Creature](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/Creature.dbd), [CreatureDisplayInfo](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/CreatureDisplayInfo.dbd) and eventually model dependencies. Creature.DisplayID has an explicit display target. | The existence of a client creature record/display does not establish a complete NPC catalogue, spawn locations, patrols, vendor stock or quest-giver relations. “Where is this NPC?” needs actual location evidence from an admitted source, not a model's coordinates or a similarly numbered ID. Start with references and appearance context; do not promise a complete world population. |
| **Dungeons and encounters:** “Which encounters belong to this instance, and what does the journal describe?” | [JournalInstance](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/JournalInstance.dbd), [JournalEncounter](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/JournalEncounter.dbd), [DungeonEncounter](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/DungeonEncounter.dbd), Map. Explicit instance/encounter/map references support a promising readable hierarchy. | Difficulty masks, condition references, journal sections and localized text need interpreted, tested rules. Journal description is client presentation, not a complete combat script, verified tuning, loot probability or proof an encounter is enabled. |
| **Quests:** “Which related objectives or storyline records can this build substantiate?” | [QuestV2](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/QuestV2.dbd), [QuestObjective](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/QuestObjective.dbd), [QuestLineXQuest](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/QuestLineXQuest.dbd), [QuestPOIBlob](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/QuestPOIBlob.dbd). QuestV2 is a small identity/bit/theme definition, not a full quest narrative. | QuestObjective.ObjectID is polymorphic according to Type; its comments are research hints, not a universal FK contract. QuestPOIBlob explicitly warns that not all objective records are in the client. Storyline ordering does not prove prerequisite/unlock edges. Full text, starts/ends, rewards, eligibility and live availability may require additional evidence; missing client records must remain unknown. |

Other useful candidates are spells, mounts/collectibles, achievements and professions. Their research questions include “what effect or requirement changed?” and “which records connect this reward to its source?”. They should be assessed after the first semantic slice rather than developed together. For example, [SpellEffect](https://github.com/wowdev/WoWDBDefs/blob/b9a63096cdd99b26967f17f9515377ae62cadfd7/definitions/SpellEffect.dbd) includes difficulty and effect-dependent fields; numeric similarity is not a safe generic join. Spell descriptions and base values are not a full simulator of live combat.

## Context that every area must preserve

- **Build and edition:** an ID is meaningful in its admitted product/build/table context. Cross-build or cross-edition equality must be proven, never inferred from ID alone. Record presence, absence, undecodable content and unavailable content are separate observations.
- **Locale:** localized names may come from locale-specific files; switching locale must retain the selected record identity and show missing/fallback strings explicitly. An English label is not a new record identity. Derived results must include the effective locale and schema/decoder revisions in their cache identity.
- **Content and decoding:** downloaded bytes can still be encrypted or unsupported. The [WDC5 reader](https://github.com/wowdev/DBCD/blob/e732093f8864240fc5884bd1bba6b02f3dfc0d56/DBCD.IO/Readers/WDC5Reader.cs) is concrete implementation evidence for sectional DB2 handling, not evidence that VibeMiner already supports it. A partially readable table must not silently become an empty/complete semantic view.
- **Server and hotfix context:** CDN contents describe a captured client build. Without a separately admitted overlay, do not claim it includes all later hotfixes or the live server's active rules/state. No game-folder/cache import is introduced by this proposal.
- **References:** preserve source and target column, raw value, definition revision, exact layout, confidence and resolution result. Zero may be a sentinel only under an explicit rule. Missing, ambiguous, encrypted, unsupported and not-yet-fetched targets need different outcomes. Optional text next to a raw foreign key is a presentation of a validated target lookup, not replacement of the raw value.

## External context: evidence beside the build

External sources can make a semantic view substantially more useful, particularly for quests and NPC locations. They must be opt-in providers with separate storage/provenance and licensing review. They must not overwrite captured build facts or silently change historical results.

Blizzard's [official World of Warcraft Game Data API documentation](https://community.developer.battle.net/documentation/world-of-warcraft/game-data-apis) is the first provider to evaluate. The companion [external-source research](EXTERNAL-CONTEXT-SOURCES.md) records endpoint evidence and provider constraints; it is the source for that evaluation rather than an assumed complete API. Specific field coverage, OAuth/namespace requirements, locale behavior, rate limits and redistribution conditions must be checked for each chosen use. Current/live API data must not be labelled as facts from an old CDN build.

Community datasets or authored research may later contribute quest context, locations or annotations. Evaluate each actual provider's authoritative documentation and terms first; neither a public website nor its IDs establish permission or compatibility. User-supplied annotations are another future source, clearly labelled as authored interpretation. This proposal authorizes no scraping, new network source, import feature or background API calls.

For every added contextual claim retain provider, source URL/object identity, fetch time, source revision where available, edition/region/locale, asserted build/time coverage, raw source digest, attribution/license and join rule. Mark coverage as exact, compatible with evidence, current-only or unknown. Conflicts should be visible side by side. A quest chain must distinguish an explicit prerequisite from storyline order and an inferred connection.

## Proposed research sequence

1. **Deliver Tables first.** Its schema admission, typed links, optional labels, async loading and source inspection are reusable prerequisites. Semantic planning must not delay the selected build workflow or Tables delivery.
2. **Prove one useful Items slice.** Reuse the existing bounded physical Item/name work; admit a small set of actual relationships and explain every displayed value. Choose a test cohort with missing/ambiguous/encrypted/localized cases. Validate whether the result answers a real question more effectively than Tables.
3. **Prototype a route or journal question.** A textual flight route or instance/encounter outline can demonstrate meaningful navigation without first building a 3D renderer. Pick one after evaluating exact-build coverage and user interest.
4. **Run a quest evidence spike before a Quest area.** For one selected build/locale, inventory what is actually present, which edges are explicit, and what is missing. Then separately test one permitted external provider. Demonstrate how a readable quest path represents uncertainty instead of inventing a full chain.

Each step should produce a bounded issue with a user question, admitted data/joins, unsupported cases, provenance and locale rules, cancellation/progress behavior and acceptance fixtures. All acquisition/decoding remains asynchronous through application providers; background retention continues, and interactive reads retain priority. Progress is determinate only when a reliable byte/work total exists; otherwise show the current stage and completed work without a fabricated percentage. Changing a table, build or locale must fence stale completions.

No production code was changed for this research. Validation consisted of inspecting the pinned definition headers and upstream format/reader documentation; no game content was downloaded and no entity-level coverage was measured against an actual build. The proposals above require those admission checks before implementation.
